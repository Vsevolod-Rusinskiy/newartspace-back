# Правила работы с New Art Space backend

Этот файл действует для всего репозитория `newspace-back`.

## Источник общей документации

Общие документы канонически хранятся в соседнем приватном репозитории `../newspace-docs`. Старые общие Markdown-файлы внутри backend являются только указателями; полный текст читать и редактировать в `newspace-docs`.

## Обязательно перед любым изменением

1. Полностью прочитать `../newspace-docs/backlog/BACKLOG.md`.
2. Полностью прочитать `../newspace-docs/architecture/PROJECT_INTEGRATION_CONTRACTS.md`.
3. Если задача влияет на публичный сайт, SEO, URL, sitemap, каталог или кэширование, также полностью прочитать `../newspace-docs/seo/SEO_IMPLEMENTATION_PLAN.md`.
4. Для изменений схемы или `slug` дополнительно прочитать релевантные документы в `../newspace-docs/decisions/specs/backend/` и `../newspace-docs/decisions/plans/backend/`.
5. Проверить `git status --short` и релевантный diff. Считать все существующие изменения работой владельца проекта и сохранять их.
6. До правок описать владельцу затрагиваемые endpoints, таблицы, миграции, файлы, admin/frontend-потребителей и план проверок. Если команда на реализацию ещё не дана, дождаться её.

## Неприкосновенные правила

- Не выполнять `git reset`, `git checkout`, `git clean`, `git stash`, rebase, commit, push и не перезаписывать параллельные изменения без отдельной команды владельца.
- Не выполнять deploy и не применять production-миграции. Production по умолчанию использовать только для read-only проверок.
- Не изменять формат API-ответа без сквозной проверки frontend и admin.
- Сохранять контракт картин: `POST`/`PATCH` возвращают сущность, список возвращает `{ data, total, page, pageCount }`; admin сам формирует ожидаемую React Admin обёртку `{ data }`.
- Не добавлять `slug` в модели, DTO или БД: человекочитаемый slug формируется frontend.
- `artStyle` сейчас необязателен. Не усиливать DTO/DB-ограничения без миграции существующих данных и отдельного решения.
- Не использовать и не проверять реальным удалением `DELETE /paintings/:id` и массовое удаление до исправления `NAS-BACK-001`. Существующая ошибка может удалить изображение и связи, оставив строку картины.
- Не изменять production-картину `id=185` до решения владельца по `NAS-DATA-001`.
- При работе с изображениями не переиспользовать объект существующей картины для тестовой записи и проверять уникальность `imgUrl` перед удалением.
- Schema drift исправлять новой безопасной forward-миграцией. Не редактировать историю `SequelizeMeta` вручную и не откатывать БД переключением git-ветки.

## Проверка изменений

Перед заявлением о готовности backend-изменения выполнить подходящие проверки, обычно:

```bash
yarn test --runInBand
yarn prettier-check
yarn build
yarn db:migrate:status
git diff --check
```

Команда `yarn lint` в этом репозитории запускается с `--fix`, поэтому не использовать её автоматически поверх параллельных изменений. При изменении API-контракта, CRUD или изображений дополнительно проверить соответствующие тесты и адаптацию в `newspace-admin`, а при влиянии на публичные данные — в `newspace-front`.

## Порядок текущих работ

Сначала завершить утверждённый SEO-план. После этого отдельным этапом проверить фактическое CRUD-поведение локальных backend и admin, включая загрузку, замену и удаление изображений, и только затем написать недостающие CRUD-тесты. Удаление покрывать как корректный успешный сценарий только после отдельного исправления `NAS-BACK-001`.
